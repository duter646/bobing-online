# 产品需求文档

## 1. 产品定位

“博饼在线”是一款还原围桌轮流博饼氛围的实时多人网页游戏。它解决异地亲友、分散办公团队无法围在同一张桌旁参加博饼的问题。

产品核心不是单人抽奖，而是：一起进入同一个房间、按顺序投掷、共同见证结果、争夺有限奖品。

## 2. 目标用户

### 2.1 聚会组织者

- 家庭聚会的发起人。
- 公司部门活动的主持人。
- 同学、社群活动的组织者。

他们需要快速开房、配置奖品、邀请成员并处理临时离线等情况。

### 2.2 普通参与者

- 通过微信中的链接或二维码进入。
- 不愿进行复杂注册。
- 主要使用手机，可能处于弱网环境。

他们需要一眼看懂轮到谁、自己博到了什么、桌上还剩什么。

## 3. 成功标准

MVP 的核心验收指标：

- 新用户从打开链接到进入房间不超过 10 秒，到创建房间不超过30s。
- 95% 的房间事件在正常网络下 1 秒内同步到其他成员。
- 断线一段时间后自动托管 ，10 分钟内返回，可恢复原座位和完整状态。
- 保证规则严谨测试通过：不能跳人等违规情况。同一个投掷请求即使重复发送，也只能产生一条投掷记录。
- 规则引擎对全部 46,656 种有序骰子组合均能返回确定结果。
- 服务重启后，已落盘的房间可以恢复到最近一次快照；最多丢失范围由快照策略明确限定。

## 4. MVP 用户流程

### 4.1 创建房间

1. 用户填写昵称并创建房间。
2. 系统生成短房间码和分享链接。
3. 房主选择规则模板。
4. 房主选择“传统 63 份”或自定义奖品。
5. 房主分享链接或二维码。

### 4.2 加入与准备

1. 参与者打开链接。
2. 填写昵称；系统保存匿名会话凭证。
3. 加入大厅并自动分配座位。
4. 房主确认人数、顺序和奖品后开始。

### 4.3 进行游戏

1. 服务端广播当前玩家。
2. 当前玩家抓取骰子并拖动，释放时产生投掷位置、方向和力道。
3. 服务端验证轮次和投掷参数，根据力度计算“跳猴”概率，再生成最终结果。
4. 所有客户端使用同一投掷参数和结果播放 3D 动画。
5. 服务端判奖、扣减奖品并广播新状态。
6. 轮到下一名仍在房间中的玩家。

### 4.4 结束

满足房主配置的结束条件后：

- 房间进入结束状态，不再接受投掷。
- 展示状元、每人获得的奖品和完整开奖记录。
- 生成适合分享的战报页面。

## 5. 功能需求

### 5.1 身份与会话

- `P0` 支持匿名游客会话。
- `P0` 登录注册为可选能力，进入页面时不主动弹出登录框。
- `P0` 支持邮箱和密码注册，注册时填写默认名字；使用邮箱和密码登录，不使用邮箱验证码。
- `P0` 登录用户进入时自动填充默认名字；游客手动填写本局名字即可进入。
- `P0` 同一浏览器返回时自动恢复身份。
- `P0` 昵称长度、字符和重复昵称有明确提示。
- `P1` 支持头像上传或预设头像。
- `P2` 微信小程序登录后可绑定历史游客记录。

### 5.2 房间大厅

- `P0` 创建房间、输入房间码加入、链接直接加入。
- `P0` 房间人数限制为 2～12 人。
- `P0` 展示成员、座位、房主和连接状态。
- `P0` 只有房主可以开始游戏。
- `P0` 开始后默认不允许新成员占用玩家座位，可作为观众进入。
- `P1` 房主调整座位、移除成员、锁定房间。
- `P1` 房主离开时自动或手动移交房主。

### 5.3 规则与奖品配置

- `P0` 提供“厦门传统版”规则模板。
- `P0` 提供传统 63 份会饼库存模板。
- `P0` 支持修改各档奖品名称和数量。
- `P0` 开始后锁定规则和奖品配置。
- `P1` 保存房主最近使用的配置模板。
- `P1` 提供若干地方规则变体。

### 5.4 对局

- `P0` 严格按座位顺序轮流。
- `P0` 只有当前玩家可发起投掷。
- `P0` 当前玩家可以控制抓取位置、拖动方向和投掷力道。
- `P0` 位置和方向影响动画轨迹；过大力度会提高服务端判定“跳猴”的概率。
- `P0` 未触发跳猴时，六枚骰子保持相互独立、1～6 等概率。
- `P0` 服务端生成六枚 1～6 的骰子。
- `P0` 奖项由共享规则引擎计算，并由服务端确认。
- `P0` 所有结果具有房间内单调递增的序号。
- `P0` 重复命令不会重复扣减库存或增加记录。
- `P0` 展示本次奖项、剩余奖品和当前状元。
- `P0` 玩家断线超过宽限期且轮到其投掷时，由服务端自动跳过；连续离线席位会一次越过，全员离线时保留当前回合等待重连。
- `P1` 房主暂停、继续、手动跳过当前玩家。
- `P1` 提供表情喝彩和固定文本聊天，不开放自由文本聊天。

### 5.5 重连与恢复

- `P0` 客户端重新连接后提交本地最后事件序号。
- `P0` 服务端返回增量事件；无法增量恢复时返回完整快照。
- `P0` 同一身份在新标签页连接时，旧连接降为只读或被替换。
- `P0` 服务端定期和在关键事件后保存快照。

### 5.6 战报

- `P0` 展示最终状元和个人奖品列表。
- `P0` 展示全部投掷记录。
- `P0` 提供只读战报链接。
- `P1` 生成海报图片。
- `P1` 房主导出 CSV。

### 5.7 统计信息

- 用户掷出各个奖项的次数和频率。
- 用户获得的各档奖品数量。
- 用户参与及完成的对局次数。
- 已完成对局的累计游玩时间。
- 个人累计统计仅向已登录用户开放，并跨登录会话累计；游客仍可查看所在房间的本局战报。

## 6. 房间状态

```text
LOBBY ──开始──> PLAYING ──暂停──> PAUSED
  │                │                │
  │                ├──结束─────────> FINISHED
  │                │                │
  └──过期─────────> EXPIRED <───────┘
                   PAUSED ──继续──> PLAYING
```

状态转换只能由服务端执行。每次转换必须写入事件日志，并增加 `roomVersion`。

## 7. 非功能需求

- 移动端优先，兼容最近两个主要版本的微信内置浏览器、Chrome 和 Safari。
- 首屏关键资源建议控制在 3 MB 内，Three.js 场景、较大音效和高质量资源按需加载。
- 支持用户关闭声音、震动和动画。
- 页面刷新不能造成重复投掷。
- 日志不得记录明文会话令牌。
- 房间码不能作为唯一授权凭证；管理操作必须验证房主会话。
- 默认保存对局数据 7 天，房主可以提前删除战报。
- 不依赖客户端时间决定轮次、过期或排名。

## 8. MVP 不做

- 付费购买博饼次数。
- 现金、红包或可提现积分。
- 公共大厅和陌生人匹配。
- 自由文字聊天、语音和视频。
- 复杂账号、好友、等级和成就体系。
- 多租户品牌运营后台。
- 多服务器水平扩展。

这些功能只有在 MVP 验证后才重新评估。

## 9. 验收场景

至少覆盖：

- 12 人同时加入并完成一局。
- 当前玩家连续点击投掷按钮，服务端只接受一次。
- 投掷响应返回前客户端断线，重连后结果不重掷。
- 房主断线后重新进入，仍拥有房主权限。
- 普通玩家伪造房主命令时被拒绝。
- 奖品只剩一份时两个请求不会重复领取。
- 相同规则配置下，跳猴概率随力度单调增加且不超过配置上限。
- 未触发跳猴的样本中，各骰面分布不受投掷力度影响。
- SQLite 暂时繁忙时不会导致房间状态与记录永久不一致。
- 服务重启后恢复最近快照并继续游戏。

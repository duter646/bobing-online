# 博饼规则设计

## 1. 设计原则

- 规则引擎是纯函数，不访问网络、数据库、系统时间或界面。
- 输入为六枚骰子的点数和规则配置，输出为结构化奖项结果。
- 骰子顺序不影响奖项判定。
- 奖项判定、状元比较和奖品发放是三个独立步骤。
- 地方差异通过版本化的规则模板表达，不能散落为界面条件判断。

## 2. 输入与输出

建议接口：

```ts
type DiceFace = 1 | 2 | 3 | 4 | 5 | 6;

interface RollInput {
  dice: readonly [DiceFace, DiceFace, DiceFace, DiceFace, DiceFace, DiceFace];
  presetId: string;
}

interface AwardResult {
  primaryAward: AwardCode;
  secondaryAwards: AwardCode[];
  championRank?: ChampionRank;
  normalizedDice: DiceFace[];
}
```

`championRank` 用于两个状元结果之间比较，不能只按展示名称比较。

## 3. 基础奖项

以下作为默认“厦门传统版”的候选规则，最终优先级见待确认事项。

| 奖项    | 基础组合            |
| ----- | --------------- |
| 状元插金花 | 四枚 4，加两枚 1      |
| 六勃红   | 六枚 4            |
| 六勃黑   | 六枚相同且不是 4       |
| 五红    | 五枚 4，加任意一枚非 4   |
| 五子登科  | 五枚相同且不是 4，外加另一枚 |
| 状元    | 四枚 4，加两枚其他点数    |
| 对堂    | 1、2、3、4、5、6 各一枚 |
| 三红    | 三枚 4            |
| 四进    | 四枚相同且不是 4       |
| 二举    | 两枚 4            |
| 一秀    | 一枚 4            |
| 未中奖   | 不满足以上条件         |

四进剩余两枚中若还包含 4，可能同时产生一秀或二举，作为 `secondaryAwards` 返回。是否实际领取附加奖品由房间模板控制。

## 4. 传统奖品库存

| 奖项档位 | 数量  |
| ---- | ---:|
| 状元   | 1   |
| 对堂   | 2   |
| 三红   | 4   |
| 四进   | 8   |
| 二举   | 16  |
| 一秀   | 32  |
| 合计   | 63  |

高级状元类型仍从“状元”库存中产生，不额外增加传统库存。

## 5. 判定顺序

代码必须按照从特殊到一般的顺序判定，以免五红被判成普通状元、四进带一秀被判成一秀。

建议顺序：

1. 六枚同点特殊组合。
2. 五红、五子组合。
3. 状元插金花>普通四红状元。
4. 对堂。
5. 三红。
6. 四进及其附加奖项。
7. 二举。
8. 一秀。
9. 未中奖。

状元类型之间的最终排名由单独的 `compareChampion(a, b, preset)` 完成。

## 6. 发奖规则

一次投掷的处理顺序：

1. 判定完整奖项结果。
2. 根据规则模板确定可领取的奖品档位。
3. 检查对应库存。
4. 在同一服务端事务中扣减库存并写入领取记录。
5. 更新当前状元持有人。
6. 广播结果和新库存。

若命中档位已经领完：

- 仍记录博得的奖项。
- 显示“博中，但该档奖品已领完”。
- 默认不自动降级领取较低档奖品。

## 7. 状元处理

状元的“判定”和“奖品归属”分开：

- 每次状元结果均进入记录。
- 房间维护当前最强状元及持有人。
- 新状元更强时替换当前状元。
- 最终结束时再确定状元奖品归属，可避免中途反复转移实物奖品。

是否允许同一玩家多次刷新自己的状元结果，由规则模板决定。

## 8. 结束条件

MVP 支持两个结束条件：

- `ALL_PRIZES_CLAIMED`：所有启用的奖品库存归零。
- `MAX_ROUNDS`：每人完成设定轮数。

默认使用扩展的 `ALL_PRIZES_CLAIMED`：所有奖品领取完后，先完成当前轮，再额外完成一整轮，随后结束。最终状元以整局出现的最高状元为准；房主仍可人工结束作为兜底。

## 9. 跳猴概率

“跳猴”不由客户端物理模拟直接决定，而由服务端根据规范化力度计算概率。位置和方向在 MVP 中只影响动画，避免通过构造异常坐标改变中奖概率。

初始建议参数：

```ts
const threshold = 0.8;
const maxProbability = 0.25;
const normalized = clamp((strength - threshold) / (1 - threshold), 0, 1);
const outsideProbability = maxProbability * normalized ** 2;
```

对应关系：

| 力度 | 跳猴概率 |
|---:|---:|
| `0.00～0.80` | `0%` |
| `0.85` | `1.5625%` |
| `0.90` | `6.25%` |
| `0.95` | `14.0625%` |
| `1.00` | `25%` |

该曲线属于首轮可玩性参数，不是最终传统规则，必须通过真机试玩调整。阈值、上限和指数写入版本化规则配置，并在房间开始后锁定。

服务端处理顺序：

1. 校验并限制力度在 `0～1`。
2. 使用规则配置计算跳猴概率。
3. 使用密码学安全随机数决定是否跳猴。
4. 若跳猴，返回 `OUTSIDE`，不再生成有效骰面和奖项。
5. 若未跳猴，再独立生成六枚均匀骰子并进行奖项判定。

客户端根据服务端结果播放匹配动画：跳猴时至少一枚骰子受控飞出碗外；正常结果必须留在碗内并收敛到指定骰面。

## 10. 测试要求

### 10.1 黄金用例

为每一种奖项和边界组合编写明确用例，包括：

- `[1, 1, 4, 4, 4, 4]`
- `[4, 4, 4, 4, 4, 4]`
- 所有非 4 的六同。
- 五红带 1～6。
- 每一种五子及不同尾数。
- 普通四红的全部剩余点数组合。
- 对堂。
- 四进带零、一或两枚 4。

### 10.2 穷举测试

枚举全部 `6^6 = 46,656` 种有序输入，并验证：

- 每个输入都得到合法结果。
- 任意排列得到相同结果。
- 主奖项只能有一个。
- 奖项名称与排名均来自已注册模板。
- 统计分布固定，规则变更时需要显式更新快照。

### 10.3 属性测试

- 输入少于或多于六枚骰子时拒绝。
- 出现 1～6 之外的点数时拒绝。
- 比较函数满足自反、反对称和传递性。
- 跳猴概率在阈值内为零、超过阈值后单调递增、最大不超过配置上限。
- 固定随机输入时，服务端跳猴判定可重复测试。
- 未触发跳猴时，力度不参与骰面生成。

## 11. 已确认的地方规则

- 状元优先级：状元插金花 > 六勃红 > 六勃黑 > 五红 > 五子（五黑）> 普通状元。
- 同一类型状元按照剩余骰子的点数比较大小。
- 四进带一秀或二举时，同时领取对应附加奖品。
- 状元奖品不在过程中反复追缴，对局结束后由整局最高状元获得。
- 六勃红不通吃桌面剩余奖品。
- 所有奖品领取完后，完成当前轮并再进行一整轮，然后结束游戏。

这些选项将固化成带版本号的规则预设，例如 `xiamen-traditional-v1`。

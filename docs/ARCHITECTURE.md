# 系统架构

## 1. 架构目标

首版按单机部署设计，重点保证规则正确、实时状态一致和部署简单；同时保留未来迁移到微信小程序、PostgreSQL 和 Redis 的边界。

## 2. 组件划分

## 3. 代码边界

### `packages/domain`

- 博饼规则与状元比较。
- 房间及对局状态机。
- 奖品库存规则。
- 不依赖 Vue、Socket.IO、SQLite 或 Node 专有 API。
- 可直接复用于 H5、服务端测试和小程序。

### `packages/protocol`

- HTTP 请求与响应类型。
- Socket 事件名称和载荷类型。
- 错误码、协议版本、快照结构。
- 不包含业务实现。

### `apps/server`

- 创建游客会话和房间。
- 鉴权、限流和输入校验。
- 执行房间命令。
- 生成骰子结果。
- 持久化事件与快照。
- 广播状态变化。

### `apps/web`

- 页面、交互、声音和动画。
- 使用 Three.js 渲染场景，使用 cannon-es 进行表现层轻量刚体模拟。
- 本地保存游客会话凭证。
- 根据服务端结果播放骰子动画。
- 维护最后收到的事件序号并发起重同步。
- 不在客户端决定真实骰子结果或扣减奖品。

## 4. 服务端权威模型

客户端发送的是“投掷意图”，不是骰子结果：

```text
客户端：我在 roomVersion=18 时请求投掷，commandId=abc
服务端：验证身份和轮次 → 生成六枚骰子 → 判奖 → 持久化 → 广播事件
```

随机数使用 Node.js `crypto.randomInt(1, 7)` 或等价的密码学安全随机源。动画使用服务端返回的视觉种子以及玩家的投掷参数，但动画碰撞结果不得覆盖服务端点数。

## 5. 受控 3D 投掷

当前玩家的操作产生规范化投掷参数：

- 抓取位置：限制在允许的场景范围内。
- 拖动方向：归一化二维或三维方向。
- 力道：压缩为 `0～1`，同时作为服务端跳猴概率的输入。
- 持续时间：只用于动画节奏和异常检测。

服务端校验并广播这些参数，使它们真实影响六枚骰子的初速度、旋转、落点分散和碰撞强度。服务端还按照锁定的规则曲线，根据过大力度计算跳猴概率；未触发跳猴时，再独立生成最终骰面并完成判奖。

客户端采用固定时间步长运行表现层物理。接近动画结束时，根据每枚骰子的目标点数施加阻尼和姿态修正，使其自然收敛；到达最大时长后直接固定到目标姿态。不同设备可以出现不影响结果的细微轨迹差异，但停止时间和最终骰面必须一致。

界面应明确说明“过大力度会增加跳猴概率；未跳猴时，不改变其他奖项概率”。完整物理引擎直接决定结果的模式作为后续实验项保留，不进入 MVP。

## 6. 内存与 SQLite 分工

### 服务器内存

- 当前房间状态。
- 在线连接映射。
- 当前轮次、房间版本和定时器。
- 最近事件缓冲区。

### SQLite

- 匿名会话摘要。
- 房间元数据和成员。
- 游戏配置、投掷和领奖记录。
- 关键事件日志与房间快照。
- 最终战报。

建议启用 WAL、外键和合理的 busy timeout。所有影响奖品库存的操作必须在数据库事务中完成。

## 7. 持久化策略

- 创建房间、开始、投掷结算、暂停、结束属于关键事件，立即持久化。
- 每次成功投掷后更新房间快照；MVP 规模下优先保证简单和可恢复性。
- 广播成功不能作为持久化成功的替代。顺序应为：验证 → 计算 → 事务落盘 → 更新内存 → 广播。
- 启动时加载未结束且未过期房间的最新快照，并重放快照后的事件。

## 8. 并发控制

每个房间使用串行命令队列，避免两个投掷同时修改状态。

同时使用：

- `commandId`：客户端生成，保证命令幂等。
- `roomVersion`：乐观并发版本，拒绝基于旧状态的管理命令。
- 数据库唯一约束：作为重复投掷的最终防线。
- 单事务库存扣减：避免库存变成负数。

## 9. 故障处理

- 客户端断线：保留座位，标记离线，不立即移除。
- 网络重复：返回原命令结果，不重复执行。
- 事件缺失：客户端请求增量；超出缓冲区则请求完整快照。
- SQLite 忙：短暂重试，仍失败则不更新内存、不广播成功。
- 服务重启：从最新快照恢复；恢复完成前房间只读。
- 房主长期离线：根据规则自动移交给最早仍在线成员，或由成员投票请求移交（P1）。

## 10. 安全

- 会话令牌只在创建时返回明文，数据库保存哈希。
- 所有输入使用共享 schema 验证。
- 创建房间、加入和投掷分别限流。
- 房间码采用足够大的随机空间并限制枚举尝试。
- 房主权限由服务端成员身份决定，不能相信客户端字段。
- 昵称和奖品名称输出时转义，避免 XSS。
- 战报链接使用不可预测的公开令牌，而不是直接暴露管理凭证。

## 11. 小程序迁移边界

微信小程序阶段复用：

- 服务端全部逻辑。
- `packages/domain`。
- `packages/protocol`。
- 规则测试和协议契约测试。

需要重做或适配：

- 登录和分享 API。
- Three.js/cannon-es 渲染适配、音频、震动和生命周期。
- 网络断线行为及 WebSocket 封装。
- 隐私授权和平台审核材料。

## 12. 后续扩展

只有出现多实例部署需求时再引入 Redis：

- 房间归属和节点路由。
- Socket.IO 跨节点广播。
- 分布式锁或按房间分片。
- 临时状态及限流。

长期历史、复杂查询或运营后台出现后，再从 SQLite 迁移到 PostgreSQL。
